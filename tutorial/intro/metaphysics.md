# 用形而上学识别问题，让设计从结构中长出来

适用场景

当你面对一个需求，直觉告诉你”这不是表面看起来那么简单“，但又说不清为什么——这时候不要用工程思维直接跳到方案，先用形而上学把问题本身的结构看清楚。

我有时候会在电脑上使用pi跑任务，然后出门溜达，我希望pi跑完以后把消息发送通过hermes发送到微信上。我要怎么设计和实现方案？

第一步：悬置现象

操作：把需求包装剥掉，只看裸现象。

需求通常是别人（或你自己）用解决方案语言描述的：”我要pi跑完通知我微信“。这不是问题，这是已经被包装过的答案。

你要做的是回到现象本身：

• 发生了什么？

• 谁在什么位置？

• 什么东西断裂了？

具体做法： 拿一张纸（或开一个文档），写下所有让你觉得”这里有点不对劲“或”这里不只是表面那个意思“的点。不要试图解释，只记录困惑。

例子（你的案例）：

困惑点	为什么困惑
事件在A处，我在B处	这不是简单的”网络传输“——是存在论上的空间分离
pi不知道”我“在等	缺失的是意向性链条，不是数据管道
我要的不是数据，是”知道“	”通知“和”被召唤“是不同的事

检验标准： 如果你写出来的困惑点全都能用”加个API调用“解决，说明你还没挖到真正的结构。继续问”为什么“——为什么需要这个API？它解决的是哪个层面的断裂？


——

第二步：范畴发明

操作：为这个领域发明基本切分。不是从已有词汇里选，是创造新的切割方式。

范畴不是标签，是关节——实在在哪里”弯折“，你就在哪里切。

具体做法：

1. 列出现象中所有”东西“——不是名词，是你在第一步中感知到的那些实体/事件/关系

2. 问自己：这些东西在存在论上是同一类的吗？ 如果不是，它们应该被切成不同范畴

3. 为每个范畴写一句话定义——定义必须说清楚”它是什么层面的事“，而不是”它做什么“

例子：

原始直觉	范畴化后	定义
”任务跑完了“	事件（Event）	在某个时空中发生的状态变化，具有内在时间边界
”我在溜达“	觉知者（Subject）	具有注意力指向能力的实体
”hermes转发“	信使（Messenger）	连接事件和觉知者的中介，功能是见证而非搬运
”微信“	通道（Channel）	觉知者已打开的感知入口
”我需要被拉回来“	召唤（Summons）	对觉知者注意力的拉动

关键检验： 每个范畴之间是否互斥？如果一个东西可以同时属于两个范畴，说明你的切割还不够锐利，需要再切。

常见错误： 把功能描述当范畴定义。”信使是传递消息的东西“——这是功能描述。”信使是见证者，将’发生‘转化为’可知的发生‘“——这是范畴定位。前者告诉你它做什么，后者告诉你它在存在论上是什么。


——

第三步：关系建模

操作：定义范畴之间的逻辑关系，搭建层级结构。

不是画流程图（那是工程思维），是建立存在论上的依赖关系。

具体做法：

1. 画一张图，节点是你的范畴

2. 用箭头标注关系类型：

  ◦ 产生：A的发生导致B的出现

  ◦ 派生：B的存在以A为前提

  ◦ 转化：A通过某种操作变成B

  ◦ 指向：A的注意力/意向朝向B

3. 分层：哪些范畴是底层的（不依赖其他范畴），哪些是派生的

例子：

事件（本体层：不依赖任何主体）
  │ 产生
  ▼
信使（见证层：将发生转化为可知）
  │ 转化
  ▼
通道（感知层：已有入口）
  │ 指向
  ▼
觉知者（意向层：注意力被拉动）


关键检验： 如果去掉某一层，整个结构是否还成立？如果去掉信使层，事件仍然发生但无人知晓——这说明见证层不是装饰，是必要条件。这种”去掉后系统塌缩“的层就是核心层。


——

第四步：边界测试

操作：拿反例和极端情况去戳你的框架，看哪里会塌。

具体做法：

对每个范畴，问：

• 如果它不存在，会发生什么？（测试必要性）

• 如果它的功能被另一个范畴替代，会怎样？（测试唯一性）

• 如果它的输入/输出是异常的，框架还能工作吗？（测试鲁棒性）

例子：

测试	结果	揭示的结构
hermes挂了	事件沉没，无人知晓	见证层是必要条件，不是可选优化
你没看微信	召唤发出但未接收	信使的承诺到”送达“为止，接收是觉知者的事
pi直接发微信	短期可行，长期耦合	执行者和信使混淆，扩展性塌
事件是”异常“而非”完成“	召唤紧迫性不同	事件类型影响召唤强度，需要显式建模

塌了怎么办： 塌了不是失败，是信号。框架在告诉你”这里还有一个你没看到的关节“。回去改定义、加范畴、或调整层级。


——

第五步：元层反思

操作：退一步，看你的框架本身。

具体做法：

1. 你用的这些范畴属于哪个更大的领域？它们可以被一个更高层的框架容纳吗？

2. 你的框架能容纳的，除了当前这个具体问题，还有哪些类似但不相同的问题？

3. 有没有什么东西在你的框架里”说不出来“？——如果有，那是边界，不是缺陷。好的框架知道自己的沉默之处。

例子：

你的框架（事件→见证→通道→召唤）属于行动-感知存在论。它不只能容纳”pi通知微信“，还能容纳：

• 多个设备间的状态同步

• 任务依赖链中的条件触发

• 多主体协作中的事件广播

但它容纳不了”实时双向对话“——那是另一个框架（交互存在论），不是这个框架的适用范围。这是边界，不是缺陷。


——

第六步：设计从结构中长出来

操作：现在才进入工程层面——但设计已经被结构决定了。

当你有了清晰的范畴和层级，设计决策不再是”选A还是选B“的权衡，而是”在这个位置上，什么符合结构“的推导。

推导规则：

结构原则	设计含义
范畴之间互斥	每个模块只承担一个范畴的功能
层间依赖单向	下层不知道上层，上层可以调用下层
见证层是必要条件	hermes不能是可选项，必须有
通道可替换	微信只是通道的一种实现，接口要抽象
召唤强度由事件类型决定	事件需要携带类型/优先级元数据

你的案例长出来的设计：

• pi只做一件事：宣告事件（HTTP POST到hermes，payload只含事件本体信息）

• hermes做两件事：见证（记录事件）+ 召唤（根据事件类型选择通道和强度）

• 微信是通道的一个adapter，可以换、可以加

• 鉴权在信使层，不在通道层

• 事件类型（完成/异常/警告）决定推送策略


——

总结：完整流程速查

1. 悬置 → 剥掉需求包装，记录困惑点
2. 范畴发明 → 在关节处切割，给每个范畴存在论定位
3. 关系建模 → 搭建层级，标注依赖和转化
4. 边界测试 → 用反例戳框架，塌了就改
5. 元层反思 → 确认框架的适用范围和边界
6. 设计推导 → 从结构推出工程决策，而非从便利凑方案
