学习单元 5：模块化与组合——分而证之，合而信之

1. 本体定位

前四个单元你一直在跟一个状态机较劲。但真实系统长这样：

锁服务 ─┐
账户服务 ─┼─> 一个大系统状态 = 各模块状态的乘积
审计日志 ─┘


如果硬写成一个巨型 schema，状态爆炸、不变量缠成一团、改一个字段全机重证。形式化建模的工程化关键，就是组合（composition）：

把系统拆成若干独立规约的模块，各自证完 safety/liveness，再用数学规则把它们的状态、操作、不变量并起来，且组合体的性质能直接继承，不用重证。

本体一句话：模块是状态空间的直积，组合是操作的可并行交错，性质靠“模块间不互相越界”自动保住。


——

2. 组合的数学骨架

状态是直积

M1 : State1, ops1, inv1
M2 : State2, ops2, inv2

M = M1 × M2
State = State1 × State2
inv  = inv1 ∧ inv2


操作分两类：

• 本地操作：只动 M1（如 Withdraw），对 M2 状态原样保留

• 跨模块操作：动两边，但必须显式声明读了哪边、写了哪边

组合不变量怎么保？

关键定理（直积组合定理）：

若 op1 保持 inv1 且不碰 State2
且 op2 保持 inv2 且不碰 State1
则 任意交错执行 op1/op2 都保持 (inv1 ∧ inv2)


不需要把两个模块摊成一个大机重新做归纳。“不碰别人状态”本身就是可证的局部性质，证一次就永久复用。

这就是形式化方法相对测试的杀手锏：测试要全系统回归，证明只要证“接口边界没越界”。


——

3. 一个完整组合例子：账户 + 锁 + 审计

模块1：账户（Unit 2 的 ATM）

Acct ::= balance : Account → ℕ
inv_acct ≡ ∀ a · balance(a) ≥ 0
Withdraw(a, amt): pre amt ≤ balance(a); post 扣款


模块2：文件锁（Unit 3/4）

Lock ::= locked:P(File); holders:File→User; waiters:File→seq(User)
inv_lock ≡ 至多一个持有者 ∧ 队首才能拿锁


模块3：审计日志（新加，极简）

Audit ::= log : seq(String)
Append(msg): post log’ = log ⌢ ⟨msg⟩
inv_audit ≡ 无（纯追加，不约束内容）


组合系统

State = Acct × Lock × Audit
inv   = inv_acct ∧ inv_lock ∧ inv_audit


现在写一个跨模块操作：AdminWithdraw(admin, a, f, amt)

语义：管理员要先持文件锁 f，才能给账户 a 做超额提款，并写一条审计。

pre:  holders(f) = admin          // 锁模块保证的权限
      amt ≤ balance(a)            // 账户模块自己的前置
post:
  balance‘ = balance ⊕ {a↦balance(a)-amt}   // 动 Acct
  holders’ = holders ; locked‘=locked ; waiters’=waiters   // 锁不动
  log‘ = log ⌢ ⟨”admin {admin} withdrew {amt} on {a}“⟩     // 动 Audit


证明只需要三行局部论证：

1. 动 balance 的部分满足 Withdraw 原证 → inv_acct 保持

2. 锁状态原样复制 → inv_lock 没被碰，pre 里已校验持锁人

3. Audit 只追加 → inv_audit 平凡保持

全程没有重新证“锁至多一个持有者”这种已经证过的东西。 这就是组合的价值。


——

4. 组合里最容易翻车的三个坑（重点）

坑	表现	怎么防
隐式读别人状态	操作说“只动账户”，pre 里却偷偷读了 holders(f) 却不声明依赖	规约里显式写 uses: Lock.holders，做接口依赖表
跨模块破坏不变量	审计模块本来无约束，某天加了“清日志”操作把 log 截断，结果别的模块假设“审计不可删”	跨模块假设必须写成显式共享不变量，不能靠默契
伪组合（实际耦合）	两个模块状态拆开了，但每个操作都同时改两边，等于没拆	检查“本地操作占比”，真耦合就该合并成一个模块重新抽象

口诀：组合不是把代码文件分开放，而是把“谁允许碰什么状态”写成可检查的接口契约。


——

5. 再往上一点：组合 + 细化可以叠加

组合和 Unit 3 的细化是乘法关系：

抽象层：Acct_abs × Lock_abs        （高层粗规格）
            ≿
具体层：Acct_impl × Lock_impl × Audit_impl


只要每个模块各自细化成立、跨模块操作不越界，整体细化自动成立。

工业里 B 方法、TLA+ 的“模型检查大系统”就是靠这招把状态空间拆开验证再拼回来。

6. 本单元练习

给你一个新需求，练“拆模块 + 写跨模块操作 + 只做局部论证”：

系统加一个 配额模块 Quota：每个用户每天最多发起 10 次 Withdraw。

Quota ::= used : User → ℕ; day : Day

inv_quota ≡ ∀ u · used(u) ≤ 10

任务：

1. 把 Quota 作为新模块加进 Acct × Lock × Audit × Quota，写出组合不变量

2. 改写 AdminWithdraw，把“扣配额”加进去，只动 used(u)，其余模块原样保留

3. 列出你这次证明 inv_quota 保持时只需要复用的局部论证（不要重写账户扣款的证明）

4. 指出一个“隐式耦合坑”：如果某天产品说“管理员提款不计入配额”，你要在规约哪一行改、会不会悄悄破坏别的不变式？

（直接发我，我帮你盯第 4 问——这是最考“组合契约意识”的地方，很多人会直接改操作体却忘了更新接口依赖声明。）


——

7. 过关标准

1. 能用直积把多个模块拼成系统，不摊成大单体

2. 跨模块操作显式声明 uses / writes，不偷偷读别人状态

3. 证明时只做“局部复用”，不重复证已证过的不变量

4. 能识别“改一个产品规则”会落在接口契约的哪一行，而不是改代码凭感觉
