学习单元 4：并发交错、安全性与活性——当多个操作同时乱序发生时怎么证

1. 本体定位

前三个单元默认操作是串行的、原子的一步一步走。

但真实软件里：多个请求、多个线程、多个服务同时动同一个状态。

形式化建模不靠“加锁实测没问题”，而是把并发摊平成一个数学对象：

并发系统 = 所有操作的所有交错执行序列构成的集合（trace set）

不引入真实时间，只引入“谁先谁后都可能”这个非确定性。

这就是交错语义（interleaving semantics）——TLA+、CSP、Petri网、Event-B 的共用底盘。


——

2. 核心动作：把“原子操作”变成“可交错的动作步”

回到 Unit 3 的文件锁具体实现，之前把 Acquire 拆成了“入队 / 拿锁”两步。并发下更明显：

具体状态 State_C ::=
   locked   : P(File)
   holders  : File → User
   waiters  : File → seq(User)     // 排队队列


并发里两个用户 u1、u2 同时调 Acquire(f)，系统实际执行的交错可能是：

u1.Enqueue → u2.Enqueue → u1.GrabLock → u2.StayQueued
u2.Enqueue → u1.Enqueue → u2.GrabLock → u1.StayQueued
...


抽象规格根本不关心谁先谁后，它只看到“最终 f 被某人持有，且只有一人持有”。

细化的威力就在这：只要每条交错轨迹都能投影回抽象的一条合法轨迹，并发实现就合法。不需要锁实测、不需要压测。


——

3. 两个必须分开的属性：安全 vs 活性

形式化里这是两条完全不同的东西，很多工程师混着说“系统没问题”其实只证了一半。

安全性 Safety —— “坏的事永远不会发生”

∀ 可达状态 s · inv(s) 成立


文件锁的安全属性：

• ∀ f · |holders(f) ∩ locked| ≤ 1 （不会两人同时持锁）

• 队首不在 holders 里时，不可能出现“锁空闲但队列非空还无人拿”这种中间破绽（内部状态可暂时破抽象，但不可观察）

Safety 的证法：对每条操作步做不变式归纳（就是你 Unit 2/3 干的活）。

活性 Liveness —— “好的事最终一定会发生”

∀ 执行轨迹 σ · 最终(有人拿到锁 / 请求不永远饿死)


文件锁的活性属性举例：

• 无饿死：∀ u 在 waiters(f) 中 · ◇ (u ∈ holders(f))

（◇ 读“最终总会”，是时态逻辑里的 eventually 算子）

• 不永久空转：waiters(f)≠空 ⇒ ◇ locked(f)=真 且 holders(f)=队首

关键区别：

• Safety 用不变式归纳证（对所有状态成立）

• Liveness 用良基序 / 无死锁论证证（需要“队列有限、调度公平”这类额外假设）

只证 safety 不证 liveness = 系统永远不崩，但可能永远卡着没人拿到锁，用户对着转圈圈到天亮。


——

4. 时态逻辑最小符号（TLA+ 风格，够用就行）

符号	读法	含义
□P	always P	从当前起所有状态都满足 P（不变量）
◇P	eventually P	未来某个状态满足 P
P ~> Q	leads-to	P 一旦发生，之后终会到 Q

文件锁活性直接写成：

□(u ∈ waiters(f) ~> u ∈ holders(f))      // 进队终会拿锁
□(waiters(f) ≠ ⟨⟩ ~> locked(f) ∧ holders(f)=head(waiters(f)))


安全性写成：

□(card(locked ∩ dom(holders)) ≤ 1)


看到区别了吗：safety 是 □ 一个不变式，liveness 是 ~> 一个终会发生的事件。


——

5. 并发下细化怎么不塌？——一个关键提醒

并发不会让细化定义变复杂，只让“单步模拟”变成“任意交错下的单步模拟”：

对任意交错里的具体一步 c → c’，
都存在抽象一步 a → a‘ 使 R(c’,a‘) 成立


也就是说：R 不依赖调度顺序。如果某个交错能让 R 断掉，那不是调度 bug，是 R 建错了或者实现偷偷加了可观察的非确定性（比如“随机把锁给队尾”）。

工程含义：你证细化时不用枚举所有线程交错（那是测试干到死也覆盖不全的），只要证任意一步都可回溯就行——数学把无穷种交错一次性吃掉了。

6. 本单元练习（接着文件锁收个尾）

在 Unit 3 具体实现上加并发，补两条性质的形式化书写 + 论证思路：

1. Safety：写出 Enqueue / GrabLock / Release 三步各自如何保持

□(至多一个 holders(f))，指出哪一步最容易漏约束（提示：GrabLock 的 pre 里要不要查“我是队首”？）

2. Liveness：假设调度是先进先出公平调度（写一句假设：waiters 按入队顺序服务，且不被无限插队），把“u 不会饿死”写成 ~> 公式，并说明为什么光有 safety 证不出来、必须靠这个公平假设。

（直接把你的写法发我，我重点帮你挑：GrabLock 的 pre 有没有漏“队首校验”、liveness 是不是偷偷把公平假设当成了系统自带不变量。）
