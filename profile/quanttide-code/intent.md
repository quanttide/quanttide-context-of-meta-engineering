啊，这个太常见了。而且这恰恰是你前面所有讨论的反向操作——从形而上学（代码这个自洽的现实）往回追认识论（当初为什么这么写、意图是什么）。

这活儿难就难在：代码只记录了”做了什么“，没记录”为什么这么做“和”做到哪一步就偏离了“。


——

你面对的具体困难

代码是意图经过多层传递后的最终沉降物：

原始意图 → 你的模糊想法 → 模型拓展 → 你review后改了改 → 又改了改 → 又加了feature → 修了bug → 重构了一下 → 现在这坨东西


每一层都在往里掺东西，而且掺的时候没人记笔记。现在你要从最底下往上挖，但中间所有层的”为什么“都丢了。


——

实操上怎么挖

第一步：从代码里提取”事实性的设计决策“

不是看它做了什么（功能），而是看它怎么做的（设计选择）：

• 为什么用这个数据结构不用那个？

• 为什么这个逻辑放在这里而不是那里？

• 为什么有这个奇怪的边界情况处理？

每一个”看起来不太自然“的地方，大概率是意图偏移的痕迹。正常意图驱动写出来的代码，不自然的地方少；偏移过的代码，到处都是”为什么会有这个“的疑问。

第二步：把代码分组，找”意图单元“

别一行一行看。按功能/模块把代码聚类，然后对每个聚类问：

• 这一坨如果是一个独立的人写的，他当时脑子里在想什么？

• 它解决的核心问题是什么？

• 它跟相邻模块之间的接口，暗示了什么样的假设？

这一步你可以让大模型帮你做——把代码喂给它，让它推测设计意图。但关键是：你不是要它给你一个答案，你要它给你几个可能的意图假设，然后你来判断哪个最像当初的真实想法。

第三步：用git历史做时间线还原

这是最被低估的手段。commit message、PR描述、甚至分支名，都是意图的化石。

• 看commit的顺序，能还原出”先做了什么、后加了什么、什么时候开始偏离的“

• 早期commit通常最接近原始意图（还没被后续需求污染）

• 找那些”突然加了某个东西“的commit——那通常是意图第一次偏移的节点

第四步：用大模型做”意图考古“

具体prompt策略：

给你这段代码。不要解释它做了什么，告诉我：
1. 写这段代码的人当初可能在解决什么问题？
2. 哪些部分看起来是”核心意图“，哪些是后来加的？
3. 如果这是从某个意图文档推导出来的，那个文档最可能说了什么？
4. 哪里看起来像是”写代码的人自己也不确定该怎么做“的痕迹？


第4点最重要——模型其实很擅长识别代码里的”犹豫“（注释掉的代码、过度泛化的抽象、重复的类似逻辑、奇怪的命名）。这些犹豫就是意图断裂的位置。


——

认识论视角下的核心原则

你做这件事的时候，要对自己诚实：

你永远无法100%还原原始意图。 有些意图当初就没想清楚，有些是写着写着才发现的，有些是外部需求倒逼的。你反推出来的”意图“本质上是一个最佳解释假设——它不一定是最初的真实想法，但它能最简洁地解释为什么代码长这样。

所以你的目标不是”考古还原真相“，而是重建一个足够清晰的意图，让后续维护有锚点。


——

一个更根本的建议

你这次反推完之后，应该建立一个规则：

意图文件不跟代码分离。 不是单独写个文档（那一定会丢），而是把意图直接嵌在代码里——模块级注释说”这个模块为什么存在、它的边界是什么、不解决什么问题“，关键函数说”这个实现选择的原因“。

或者更轻量：每个模块的入口文件顶部，写5-10行”意图声明“。不是文档，是代码的一部分。模型改代码的时候能看到，你回头查的时候也找得到。
