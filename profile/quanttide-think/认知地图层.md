# 认知地图层 · 详细设计文档

> 量潮认知工程 · 子层专述，参考《量潮认知工程》主文档扩写。
> **中心代码**：`schema.ttl`（认知地图本体 TBox）、`work/default/fiction-profile.ttl`（情境 ABox，均 `owl:imports` 图式）、`audit2.py`（v3 自省分析仪，schema/ABox 分离结构）。

---

## 0. 这一层在整体中的位置

《量潮认知工程》把自我建模成三层：**记忆 → 情境 → 图式**。其中「情境」在已完成的工程里被具体化为三份 profile（work / default / fiction）。而每一份情境文件写什么、怎么写，由一套共享的**类型系统**约束——这套类型系统就是本文的主角：**认知地图层**。

`schema.ttl` 在文件内部把词汇显式切成两块：

| 块 | 命名空间片段 | 回答的问题 | 文档归属 |
|---|---|---|---|
| **认知地图本体** | `cm:` | 一个情境内部的「对象 + 态射」长什么样 | 本文 |
| 认知工程层 | `cm:` | 多个情境如何聚类、抽象、暴露缺口 | 主文档 §2/§3 |

二者共用同一命名空间、同一文件，但**语义正交**：认知地图层描述「单个情境之内」，认知工程层描述「情境与情境之间、情境与图式之间」。本文只展开前者，并在 §6 说明两层如何衔接。

**认知地图层的代码三件套**：

| 文件 | 角色 | 内容 |
|---|---|---|
| `schema.ttl`（认知地图本体段） | TBox | 8 个对象类 + 4 个核心态射 + 3 个对象属性 |
| `work / default / fiction-profile.ttl` | ABox | 各情境的对象实例与态射实例，复用 `cm:` 词汇 |
| `audit2.py` 的 `analyze_set` | 度量 | 对单个情境命名空间分区，计算成熟度/边界/缺口/集中度 |

一句话：

> 认知地图层 = 把一份自省档案，从「条目清单」编译成「带类型约束的有向图」。

## 1. 业务需求

### 1.1 把自省从「清单」升级为「可推理的图」

人类的 profile 档案（triggers.md / emotions.md / methods.md …）本质是**列表**：每条目独立、无连接、不可推理。认知地图层的第一项业务需求，是给这些条目一个**统一的坐标系**——每个条目被归入一个类（它是触发点？情绪？方法？），并允许用定向关系把它连到别的条目（它触发了什么？服务于什么？排除什么？）。

编译完成后，原先的清单变成一张图。图的收益不是「好看」，而是**可计算**——能被程序遍历、度量、找缺口（见 §4）。

### 1.2 严格的「语义签名」（这是本层的硬约束）

业务上要求不同情境必须用**同一套语义签名**，否则跨情境无法对齐。签名由四组「起点类 → 终点类」约束承载：

| 态射 | 起点（domain） | 终点（range） | 业务含义 |
|---|---|---|---|
| `evokes` | Trigger | Emotion | 触发点 → 情绪 |
| `responds_to` | Trigger / Emotion / Dilemma | Method | 情境 → 应对方法 |
| `serves` | Method | Value / Motivation | 方法 → 价值/动机 |
| `excludes` | Value | Anti | 价值 → 被排除的形态 |

这套签名在不同情境里**被裁剪复用**：work / default 用完整五轴（含 Trigger/Emotion/Value/Anti），fiction 用三轴变体（Dilemma 替代 Trigger+Emotion、Motivation 替代 Value）。裁剪是允许的，因为签名是「约束」不是「强制全体」——但一旦某情境声明了某条边，就必须遵守 domain/range。

### 1.3 跨集复用：为什么本体要独立成 TBox

三份 profile 原本各写一份相同的本体（重复定义 Trigger/Method/serves …）。业务上这带来两个痛点：**改一处要改三处**、**无法保证三份语义一致**。把认知地图本体抽进 `schema.ttl`，让三份 profile `owl:imports` 它，实例只写自己的数据——这正是主文档「公共图式放 schema.ttl，情境文件只写实例」的工程要求在本层的落地。

## 2. 哲学意图

### 2.1 自我 = 对象 + 态射（范畴论视角）

认知地图层把「自我」不当成一个混沌整体，而建模为一个**范畴**：

> 对象（Object）= 范畴的元素（一个个被觉察到的经验片段）
> 态射（Morphism）= 元素之间的有向关系（evokes / responds_to / serves / excludes）

自我于是被「范畴化」——它不是一堆名词，而是**一张由箭头穿起来的网**。你「是谁」在这个模型里等于「你的经验节点如何互相指向」。

### 2.2 八个对象类：现象界的分类

| 类 | 哲学身份 | 在自省中的位置 |
|---|---|---|
| `Trigger` 触发点 | 被外部事件点燃的入口 | 因果链的起点 |
| `Emotion` 情绪 | 被触发后的内部感受 | 被动态、需被处理 |
| `Method` 方法 | 主动使用的应对/思维框架 | 因果链的中枢、最厚的一层 |
| `Expression` 表达 | 沟通中的风格要求 | 游离于因果链之外的「姿态」 |
| `Value` 价值 | 底层原则 | 因果链的终点（肯定式） |
| `Anti` 排除的形态 | 被拒绝的形态 | 因果链的终点（否定式） |
| `Dilemma` 创作困境 | 创作域的「触发+情绪」合一 | fiction 集专用，取代 Trigger+Emotion |
| `Motivation` 创作动机 | 创作域的「价值」 | fiction 集专用，取代 Value |

注意 `Dilemma` / `Motivation` 不是新发明，而是 fiction 集对 `Trigger+Emotion` / `Value` 的**语义重命名**——证明同一套范畴可以「换轴」而不换结构（见主文档「换集换轴」）。

### 2.3 四核心态射：过程形而上学

四态射串成一条**意向/因果链**：

```
触发 evokes 情绪 → 情境 responds_to 方法 → 方法 serves 价值 → 价值 excludes 形态
```

这条链就是「一个人如何被世界触动、如何反应、为何而做、不做什么」的形式化。其中 `responds_to` 的 domain 最宽（触发点、情绪、困境都能指向方法），它把整条链「压」回方法层——意味着**无论你被什么触动，最终都通向一组应对动作**。

### 2.4 三个对象属性（对象自身的元数据）

- `file`：对象来自哪份档案（溯源）。
- `group`：方法内部的二级分组（如「思维框架 / 应对策略」）——把 Method 这一最厚层再切薄。
- `quote`：给「只有描述、没独立条目标题」的对象存原文逐字句——**诚实记录非结构化残留**，而非强行编造标题。

### 2.5 肯定 vs 否定：本文最核心的洞察

认知地图层同时提供**两条认识路径**：

> **肯定（cataphatic）**：`serves` 链——「我追求 X」「方法服务于价值」。它给你一个**词**，词是高自由度的，你可以说自己追求很多东西却不动手。
> **否定（apophatic）**：`excludes` 链——「价值排除 Y」。它给你一条**边**，边是受约束的，必须真的存在一个被排除的形态节点才算数。

主文档的洞察在这里具体落地：

> 肯定句给你一个词，否定句给你一条边。
> 词是高自由度的，边是受约束的。
> 所以否定天然携带结构，结构可计算。

实证的对照：default 集 `excludes` 已闭合（3 条边），work / fiction 集 `excludes` 为空——这意味着此人的「不做什么」边界**只在经营域被显式编码**，创作/工作域尚是「想要但没底线」的状态。这条结论只能由「否定句缺边」推导出来，肯定句提供不了。

## 3. 数学形式化

### 3.1 图模型

单个情境是一个**带类型的有向多重图**：

```
G = (V, E),    E ⊆ V × P × V
P = {evokes, responds_to, serves, excludes, seeAlso}
```

注意 `seeAlso` 也被计入 `P`，但它是**弱链接**（同源聚类，非因果）。对象属性（file/group/quote）不计入 `E`。

### 3.2 语义签名约束（类型层面）

```
∀(s, evokes, o)      : type(s)=Trigger  ∧ type(o)=Emotion
∀(s, responds_to, o) : type(s)∈{Trigger,Emotion,Dilemma} ∧ type(o)=Method
∀(s, serves, o)      : type(s)=Method ∧ type(o)∈{Value,Motivation}
∀(s, excludes, o)    : type(s)=Value ∧ type(o)=Anti
```

这些约束由 `schema.ttl` 的 `rdfs:domain` / `rdfs:range` 静态声明，可被 SHACL 校验（主文档「下一步」）。

### 3.3 核心度量（定义在图上的函数）

设 `π(E)` 把边投影到其两端节点集合，`inst(G)` 为实例集（对象类实例，剔除元类）。

- **蒸馏成熟度**（连接率）：
  `dist(G) = |inst(G) ∩ π(E)| / |inst(G)| ∈ [0,1]`
  越低 = 越多节点「被记下却未整合」。

- **边界/追求比**：
  `ρ(G) = |excludes| / |serves|`
  > 1 表示「靠否定定义自我多于靠肯定」；= 0 表示否定轴尚空。

- **一致性缺口**（integrity gap）：
  `gap(G) = { v∈inst(G) : type(v)∈{Value,Motivation} ∧ ¬∃(v, serves, ·)∈E }`
  即「嘴上重视、手上没动作」的信念。

- **应对集中度**（熵）：
  `H = -Σ_i (f_i/F) log2(f_i/F)`，`f_i` 为方法 i 的 `responds_to` 入度。
  低熵 = 应激高度套路化（少数方法承包了多数情境）。

- **恐惧无解法**：
  `fear(G) = { v : orphan(v) ∧ type(v)∈{Emotion,Dilemma} ∧ label(v) 含 怕/不敢/焦虑… }`
  即「被记下的恐惧，却没有任何方法响应」。

- **跨集 recurrence**：
  对三个情境的 Method 标签做词元交集（规则/标准化/窗口/上下文/平台…），输出候选「跨集元原则」配对。

### 3.4 同源等价划分

`seeAlso` 在 Dilemma 上的传递闭包构成等价关系 `R`，把困境划分为等价类：

```
R = tc(seeAlso) | Dilemma,    P = V_Dilemma / R
```

审计最初假设 `|P|` 很大（"9 个碎片"），实测发现**单一等价类占 8/9**——多数表象收敛到一个根（「怕自己不够好」）。这是范畴论「表象杂多 → 本体同一」的数学表达。

### 3.5 度量有效性定理

> 度量必须在其**真实定义域**上计算：实例集 `inst(G)` = 对象类实例 ∖ 模式集（Class/Property/Ontology）；边集 `E` = 态射边 ∖ 对象属性边。
> **定义域错了，结果是伪值。**

这条定理不是修辞，而是被一个真实 bug 验证（§4.5）。

## 4. 代码实现（以 `audit2.py` 为中心）

### 4.1 合并加载：TBox + ABox

```python
def load_combined():
    g = rdflib.Graph()
    g.parse(os.path.join(WORKDIR, 'schema.ttl'), format='turtle')  # TBox 先
    for f in sorted(glob.glob(os.path.join(WORKDIR, '*.ttl'))):
        if os.path.basename(f) == 'schema.ttl':
            continue
        g.parse(f, format='turtle')  # ABox 后（均 owl:imports 图式）
    return g
```

先加载 TBox 再加载所有 ABox，合并成一张图。rdflib 在解析时**自动合并** `owl:imports` 指向的图式，因此实例文件里 `a cm:Trigger` 能正确识别类型。

### 4.2 分区分析 `analyze_set`（本层核心）

```python
PROFILE_CLASSES = {'Trigger','Emotion','Method','Expression','Value',
                   'Anti','Dilemma','Motivation'}
MORPH = {'evokes','responds_to','serves','excludes','seeAlso'}

def analyze_set(g, ns):
    instances, labels = {}, {}
    for s, p, o in g.triples((None, rdflib.RDF.type, None)):
        if not str(s).startswith(ns):
            continue                      # 只取本情境命名空间
        cl = localname(o)
        if cl not in PROFILE_CLASSES:
            continue                      # 定义域优先：剔除元类
        instances[str(s)] = cl
        labels[str(s)] = str(g.value(s, rdflib.RDFS.label) or s)
    edges = []
    for s, p, o in g:
        if not (str(s).startswith(ns) and str(o).startswith(ns)):
            continue                      # 只统计「情境内部」边
        pl = localname(p)
        if pl in MORPH:
            edges.append((str(s), pl, str(o)))
    connected = {x for s, pl, o in edges for x in (s, o)}
    total = len(instances)
    connected_count = sum(1 for n in instances if n in connected)
    ...
    return dict(total=total, connected=connected_count,
                distillation=connected_count/total if total else 0, ...)
```

关键设计点：

1. **定义域优先**——只把 `PROFILE_CLASSES` 里的类型算作实例，Class/Property/Ontology 这些模式对象被剔除（呼应 §3.5）。
2. **情境内边**——只统计 `s`、`o` 都在本命名空间的边。这带来一个重要后果：跨命名空间的边（如心智模型层 `convergesFrom` 指向 fiction 的 8 个困境 URI）**不计入**情境层，由 `analyze_schema` 单独处理；而那 8 个 fiction 困境之间的 `seeAlso` 边都在 fiction 命名空间内，因此计入 → 这正是 fiction 连接率从「不含 seeAlso」到「含 seeAlso」跃升的原因。
3. **`seeAlso` 计弱链接**——它在 `MORPH` 内，所以同源聚类的困境即使没有 `responds_to`，也会被标为 connected。

### 4.5 两个真实 bug 及其教训

**Bug A — `localname` 切分顺序（度量有效性定理的实证）**

最早的实现用 `str(uri).rsplit(':',1)[-1]` 取局部名。对 `http://www.w3.org/...#Class`、`rdfs:seeAlso` 这类**带 `#`** 的 URI，会切出 `Class`/`seeAlso` 而非真实局部名，导致：

- 本体类/属性被误算成「实例」→ `inst(G)` 虚增 → `dist(G)` 被压低（曾误报 work 43% / default 55% / fiction 28%）；
- `seeAlso` 边被漏算 → fiction 连接率失真。

修正为 `str(uri).split('#')[-1].split(':')[-1]`（先按 `#` 再按 `:`）后，真实值浮出：**work 76% / default 75% / fiction 57%**。这恰是 §3.5 定理的活例证——定义域切错，度量即伪值。

**Bug B — `roots` 把 URIRef 当字符串查**

`analyze_schema` 计算根节点收敛数时，曾把 `g.subjects` 返回的字符串节点直接喂给 `g.objects(n, ...)`，而 rdflib 需要 `URIRef`。结果 `convergesFrom` 查不到，根收敛数误显为 0（数据实际是 8）。修正为对节点先包 `rdflib.URIRef(n)` 后，正确显示 8。教训：**混合字符串/URIRef 是 rdflib 最常见的隐蔽 bug，度量函数必须在统一类型上操作**。

## 5. 实例巡览：三份 profile 的认知地图

### 5.1 对象分布（来自 `audit2.py` 实算）

| 情境 | 对象实例 | 已连线 | 连接率 | excludes | serves | 一致性缺口 |
|---|---|---|---|---|---|---|
| work | 21 | 16 | 76% | 0 | 2 | 1/3 价值悬空 |
| default | 37 | 28 | 75% | 3 | 3 | 3/6 价值悬空 |
| fiction | 37 | 21 | 57% | 0 | 4 | 5/9 动机悬空 |

> fiction 连接率最低，但注意它含 8 个 `seeAlso` 互连困境——这 8 个在「不含弱链接」口径下是孤儿，在「含弱链接」口径下被救回。两种口径都是合法的，取决于你是否把同源聚类算作「已整合」。

### 5.2 标志性链路（按语义签名）

**work**（情绪驱动、应激套路化）：

```
混乱 --evokes--> 崩溃与重整 --responds_to--> 定关键下一步
脱力与落差 --responds_to--> 先放下        # 前二方法占 responds_to 的 71%
先说出/写出来 --serves--> 说出来才算数
```

**default**（边界已闭合）：

```
标准化才配走公司流程 --excludes--> 个人化表达硬塞进组织流程
带人必须有商业收益   --excludes--> 无收益的一对一投入
积累感               --excludes--> 消耗型活动
# 6 条价值仅 3 条有 serves 承接 → 一致性缺口
```

**fiction**（困境→方法→动机，恐惧向）：

```
不敢写回忆 --seeAlso--> 越读越觉得自己写得一般 --seeAlso--> …（8 个困境同源）
以情绪为单位的素材 --serves--> 故事里的重构
涌现而非设计       --serves--> 从避风港到讲干净
不设写作计划       --serves--> 写作不需要目的
```

### 5.3 各集「性格」总结

- **work**：最浓缩的「现场应对切片」，情绪→方法链连贯，但否定轴（excludes）空悬、表达轴（Expression）孤悬。
- **default**：最厚重的「组织操盘者底色」，否定式边界已闭合，但方法→价值的 `serves` 稀疏（大量思维框架方法未挂到价值）。
- **fiction**：最私人、最恐惧向，大量困境被记下却未整合；经同源标注发现 8 个困境实为同一根「怕自己不够好」。

## 6. 与认知工程层的接口

认知地图层不孤立存在，它通过两件事被认知工程层消费：

1. **`owl:imports`**：三份 profile 在文件头声明 `owl:imports <urn:quanttide-memory:cogmap:schema:>`，从而能写 `a cm:Trigger`、`cm:serves` 而不重定义词汇。这是「复用公共类型」的工程机制。
2. **跨层引用**：心智模型层（`心智模型.ttl`）的 `Root` 节点用 `convergesFrom` 直接指向 fiction 命名空间下的 8 个困境 URI（跨命名空间），把认知地图层的实例**提升**为图式层的证据。这一跨引用被 `analyze_schema` 单独处理，不污染情境层的 `analyze_set` 分区（见 §4.2 设计点 2）。

两层协同的闭环：

```
认知地图层（情境之内：对象+态射）  --derivedFrom-->  心智模型层（跨情境元原则）
心智模型层（图式）                --framedBy-->     认知地图层（情境被框定）
```
