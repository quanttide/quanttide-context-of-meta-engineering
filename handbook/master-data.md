# 主数据

## 定义

主数据是这样一个数据集合：假设把它拿走，可以把公司原样复制出来，那就说明它已经包含了所有关键信息。主数据的安全因此格外重要：如果被任何一个员工拖跑，或者因公司内部纷争被股东拖跑，影响都非常大。

主数据回答的是：一个系统的唯一事实源应该是哪一个。元数据是数据工程里的概念，主数据才是元工程里的概念。

## 为什么是元工程的起点

元工程最主要的起点就是元数据，先从元数据目录（或者叫主数据目录）开始。为什么这是元问题？因为元系统要回答的不是单个系统本身，而是系统之间的关系；先有数据和信息，才有可能去探究它们之间的关系。它的基础是范畴论——数学基础和哲学基础都是范畴论。

在医疗器械法律咨询公司案例中，建立主数据也是所有活动中最重要的基础步骤：要知道信息源在哪里，怎么管理这些信息源，把规则显性化。

## MDM 思维模型

MDM 本质上不是一个数据项目，而是一种处理定义权的工程方法。这一点不搞清楚，学再多匹配算法都是皮毛。

### 它解决什么问题

任何系统规模大到一定程度，都会出现同一个现象：同一件事，在不同的局部上下文里被各自定义了一遍，然后它们彼此冲突。客户在 CRM 里是一个东西，在财务系统里是另一个东西，在物流系统里又是第三个。不是数据错了，是定义权被分散了——每个子系统都有权重新定义客户，于是全局意义上「客户」这个对象就不存在了。

MDM 做的是把定义权收归一处，同时保留各处的表达权：

- 定义权 → 黄金记录（一个权威版本）；
- 表达权 → 多视图（同一实体在不同场景下的不同形态）。

这个区分极其关键。很多 MDM 项目失败，就是因为做成了「统一所有人的数据」，等于把表达权也收走了，各业务线必然抵制。只收定义权、不收表达权，是 MDM 最容易被忽略的边界意识。

### 四个构件

1. 区分「实体」和「关于实体的记录」。这是整个 MDM 的地基，也最容易被跳过。现实世界里的那个客户是实体，客观存在，不由系统决定；系统里存的这一条是关于实体的记录，是实体的一次不完整投影。MDM 处理的是多个投影如何指向同一个实体。混淆二者是灾难：把记录当实体，你会以为合并两条记录就等于消灭了一个客户；把实体当记录，你会觉得只要建一张大宽表就万事大吉。
2. 全局身份与局部身份的双轨制。实体有一个全局 ID，每个系统里有一个本地 ID，中间靠交叉引用表连接。这不是技术细节，而是一种分层认知：全局层回答「是谁」，局部层回答「在这里是谁」。拿到这个认知，能解释很多现象：银行为什么要做客户统一视图、国家为什么要建统一社会信用代码、微服务为什么要搞服务注册与发现——凡是需要先确认你是谁、再谈别的的场景，都是同一套结构。
3. 权威源映射：每个事实各归其主。客户名称以 CRM 为准，信用等级以风险系统为准，付款条件以 ERP 为准。不是哪个系统最高级，而是哪个系统对哪类事实最有发言权。往工程哲学上推：没有全局最优的真理来源，只有按事实类型分配的解释权——这是分布式系统里最难学的谦逊。
4. 变更是治理问题，不是技术问题。新增、修改、停用、合并、拆分，主数据的生命周期不是 ETL 跑出来的，是流程跑出来的：要业务审批、要审计留痕、要支持回退。它本质是对「谁有权改变定义」的管理，直接通向组织设计。

## 放进元工程

元工程研究的是工程本身怎么被组织和治理——那些不解决具体问题、而是决定问题如何被切分、由谁定义、如何一致的工程。在这个视角下，MDM 属于元工程中的语义治理层，同一层级的还有：

| 对象 | 它治理的是什么 | 对应的元工程问题 |
|:--|:--|:--|
| 元数据管理 | 数据是什么、从哪来 | 如何描述与追溯 |
| MDM | 一个对象是谁 | 如何确立身份与定义权 |
| 数据标准 | 同一概念如何表述 | 如何达成共同语言 |
| API 契约管理 | 服务之间如何约定 | 如何稳定交互边界 |
| 领域驱动设计 | 业务概念如何归属 | 如何切分与自治 |

这几件事在层次上是一样的：都是在系统内部建立一个公共层，让局部子系统不必互相认识就能协同；区别只在于它们治理的维度不同。

往上看一层，MDM 和元工程的接口在这里：元工程关心如何治理复杂性，MDM 给了一个具体答案——用身份 + 权威源 + 多视图来治理语义复杂性。

再往上看，还有一层更通用的方法论：当多个局部系统对同一对象各说各话时，不要在局部层解决（那是无限战争），而要升格一层，在元层建一个唯一的参照点。这个方法用在组织里是统一汇报口径，用在协议里是握手与版本协商，用在语言里是字典与术语表。MDM 是这个元方法在数据领域的一次实例化。

## 可带走的思维工具

- 身份与状态分离：谁 = 身份（稳定），他在哪、状态如何 = 状态（易变）。混着存，就是大多数数据混乱的起点；微服务的事件溯源、数据库的缓慢变化维度，都是这一条的不同版本。
- 共识的最小化：MDM 不追求「所有数据一致」，只追求「关键实体的关键属性一致」。全局共识代价极高，只在必须的地方建立，其他地方容忍差异。
- 治理与管控是两件事：管控是自上而下的统一；数据认责、业务 Owner、变更流程，本质是自下而上地分配权责。元工程如果要避免变成官僚工程，这个区别必须守住。
- 模型先于数据，定义先于模型：绝大多数项目反过来做——先导数据、再补标准，最后标准改不了只能将就。顺序一旦颠倒，后期所有统一动作都是补丁。

## 结论

MDM 的价值不在它产出了什么数据，而在于它在复杂系统中建立了一个所有人都认可的参照点，从而把 N×N 的互相协商降维成 N×1 的集中参照。这一条，是元工程的核心手艺之一。
